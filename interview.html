自我介绍

开场 30 秒决定面试官往哪挖。三版都给你写好并可直接复制，核心策略是每说一个项目顺手抛钩子，让对方从你最亮的点往下问。

30 秒版（电梯陈述）

用于「简单介绍下自己」这种短开场，目标：亮身份 + 一句话定位 + 抛钩子。

我是胡景晟，河南理工大学计算机科学与技术 2027 届。我做的是 AI 应用 / Agent 开发——不是「接个大模型」那种，而是把模型真正做成能用的系统：输出可用、成本可控、出错能降级。我自己从 0 到 1 上线了三个项目：一句话生成 Web 应用的 CodeCanvas、带确定性数字护栏的 RAG 客服 Mira、多 Agent 医疗分诊 triagent，全部公网可访问。技术栈以 Java / Python 为主，Spring AI、LangChain4j、FastAPI 都用过。

1 分钟版（标准开场）

被要求「详细点说」时用。结构：定位 → 一个最硬的项目讲透 → 能力收口。

我在意的是模型之外的工程问题。拿 CodeCanvas 说，它让不会写代码的人一句话生成可运行 Web 应用，核心是「需求固化 + 自检修复」闭环：把五阶段状态机（澄清→规划→生成→校验→修复）串起来，长任务里只注入固化后的需求单而非全量上下文，连续 8 轮注入量稳定在约 7k token；再用「错误位置回溯」只改出错行、按任务路由模型，综合成本降了约 75%。Mira 和 triagent 则是两个不同方向的护栏实践：一个用纯规则校验把财务数字幻觉压到 0，一个用状态机强制短路急症、让分诊安全 0 失误。我熟悉 Java/Python 全栈、RAG 检索重排、Agent 编排和 Docker/SSE 部署，能独立从 Prompt 工程做到前端交付。

3 分钟版（被要求展开时）

终面或技术负责人深聊用。结构：定位 → 三个项目各用「问题→做法→结果→复盘」讲一层。

在 1 分钟版基础上，按「问题→做法→结果→复盘」补三层： ① CodeCanvas 的痛点是大模型生成代码不可控易报错，我用确定性静态校验（标签闭合/语法/占位残留）卡住交付门槛，运行时报错由探针捕获并自动重做； ② Mira 的痛点是 RAG 幻觉和数字不可信，我让每个数字必须能在检索原文里对账，对不上就拒答，用 AST 白名单求值做纯规则校验，不用模型自查； ③ triagent 的痛点是医疗场景不能逻辑混乱，我用 Supervisor 多 Agent 分工 + 急症状态机短路，分诊和预约共享结论避免冲突。 三个项目覆盖了「生成可控 / 检索可信 / 协作安全」三条线，正好是我对 Agent 落地工程化的理解。
💡 开场就抛钩子：每说一个项目顺手点一句「这个我后面可以展开」。面试官大概率会从你最亮的点往下挖——所以三分钟版里你最熟的那段要练到能脱稿讲。

项目深挖 · CodeCanvas

一句话定位：让不会写代码的人通过一句话生成可用 Web 应用；用「需求固化 + 自修复」解决大模型生成代码不可控、易报错的痛点。技术栈 Java · Spring Boot · LangChain4j · nginx · systemd · SSE。地址 http://114.215.186.113/canvas/

你可以这样回答

整体是一条五阶段状态机：澄清 → 规划 → 生成 → 校验 → 修复。每个阶段都有明确的输入、输出契约，当前状态显式存在会话里，而不是藏在大模型的上下文里。

我故意没用纯 ReAct。ReAct 把「想」和「做」混在自由文本里，长任务特别容易跑偏、而且一旦出错几乎没法回滚——你不知道它到底卡在哪一步。状态机的好处是每一步都可观测、可重入、可审计：出错时我只需要回到「修复」阶段做局部重试，而不是把整轮对话推倒重来。本质上我把非结构化的需求固化成一份标准化 PRD + Token 预算，模型只是在这份契约上工作。

举 例比如用户说「做个待办清单」，澄清阶段我会追问「要不要分类、要不要本地存储」；规划阶段产出文件清单（index.html / app.js / style.css）和每个文件的职责；生成阶段才真正写码。如果生成完跑起来报了错，状态机不会回到澄清，而是直接进「修复」，只把错误栈喂回去修那一段——这就把「重来一次」的成本压到了最低。
如果追问「状态机怎么持久化？阶段之间怎么判定流转？」——答：会话级状态对象存 Redis / 文件，SSE 把每个阶段事件实时推给前端；阶段流转靠每阶段的结构化输出做通过/失败判定（这块我在第 6 节「结构化输出与重试」会展开）。

你可以这样回答

首轮我会把模糊的口语需求收敛成一份需求单（PRD）+ 文件清单 + 变更摘要。之后每一轮，模型只收到「需求单 + 本次变更 + 相关文件」，不再重发整段聊天历史。

这就解释了为什么 token 能砍下来：连续 8 轮对话，单轮注入量稳定在约 7k token，相比每轮把历史全量重发，注入 token 节省了约 85%，而且生成质量没有下降。

⚠ 口径必看简历里「节省 85%」指的是注入 token 的削减幅度，「成本降 75%」指的是综合调用成本（含模型路由、局部修复）。两个都真实、但口径不同。面试时先说清口径再报数，别混着说成一句「降了八成」——一旦被追问就容易自相矛盾。
举 例用户第 1 轮：「做个天气卡片」。我固化出需求单：城市输入、调用天气 API、卡片展示温度/湿度/图标。第 5 轮用户说「加个未来三天」。此时模型只拿到：原需求单 + 「新增未来三天预报」这个变更 + 涉及的 app.js 片段，而不是前 4 轮的所有来回。注入量始终在 7k 上下，不会随轮数线性膨胀。

你可以这样回答

有两层。第一层是静态校验：生成物在交给用户前，先过 4 项确定性检查——标签闭合、脚本语法、占位残留、入口可加载。这层不调模型，纯解析，过不了就根本没资格交付。

第二层是运行时探针：生成物真的在沙箱里跑起来，页面运行时报错 / 编译错误被探针捕获、回传错误栈。关键是「错误位置回溯」——我解析错误栈定位到具体文件与行号，只重写/修补出错的那一段，而不是全量重新生成。这正是成本可控的核心。

实测：12 个需求复跑，首轮通过率 100%（48/48 个页面）。

举 例生成的 app.js 第 23 行少了个分号导致语法错。探针把「app.js:23 Uncaught SyntaxError」回传，我只把 app.js 第 23 行附近那段重新生成，其余文件原样保留。如果换成全量重生成，很可能把本来对的代码改坏、还白白多花 token。
如果追问「4 项检查具体怎么定的？全量重生成和局部修补怎么选？」——按简历口径是结构与语法类；具体实现请以你代码为准。原则我说得清楚：错误是否跨文件 / 跨函数决定——能局部修就绝不重生成，跨文件才回到规划阶段。

你可以这样回答

两项叠加测出来的。第一是模型分级路由：按任务类型选不同档位模型——简单脚手架用便宜的小模型，复杂业务逻辑才上贵模型，把贵模型用在刀刃上。第二是需求固化 + 局部修复：把注入量和重生成次数都压下来了。

成本核算不是拍脑袋：我对照厂商真实价目表核 token 单价，同口径对比「全量重发 + 单模型」基线 vs「固化 + 路由 + 局部修复」方案，同一批任务实测综合成本下降约 75%。

举 例同样一个「带登录的博客」需求，基线方案每轮都把全部历史喂给最贵模型，8 轮下来注入十几万 token；我的方案第 8 轮只注入 7k、且只有规划/生成这种重活才用贵模型，轻活走小模型——两边按真实单价算，成本差就是 75%。

你可以这样回答

生成物在隔离沙箱里预览 / 运行，模型自主调用工具时，工具调用也被限制在沙箱内。这样即使生成物或工具想越权访问宿主、外部资源，也被边界挡住。

在「压不住的工具也会自主调用」这种场景，靠工具白名单 + 沙箱边界双保险：白名单决定它能调什么，沙箱决定它调了也跑不出边界。所以是「压不住也不怕乱跑」。

举 例假设某个生成应用想读服务器上的 /etc/passwd 或外连可疑地址，沙箱的网络策略和资源限额会直接拦掉，用户看到的只是一个跑不起来的页面，而不是一次真实的安全事故。
如果追问「沙箱怎么隔离？」——答容器 / 进程级隔离 + 资源限额 + 网络策略；具体实现请以你部署为准（简历提到 Docker / systemd / nginx）。别为了显得懂而瞎编到底用了哪种隔离。

项目深挖 · Mira

一句话定位：面向企业客服的多模态 RAG 问答系统，支持图片理解与来源溯源，用确定性护栏把数字幻觉压到 0。技术栈 Python · FastAPI · LanceDB · bge-small-zh · 数字校验 · 拒答护栏。地址 http://114.215.186.113/mira/

你可以这样回答

流程是：文档解析 → 切片向量化入库（LanceDB）→ 查询同时走向量召回和 BM25 召回 → RRF 倒数排名融合 → 重排序 → 拼接上下文 → 生成 + 数字护栏。

选型上，LanceDB 是嵌入式向量库、零运维，对个人项目很友好；bge-small-zh 中文召回质量够用、体积小跑得快。召回策略我做了层级切片：单一切片常截断语义，我改成「先大块保上下文、再按标题/段落细分保语义」的层级结构。再叠加 BM25 关键词召回和向量召回互补，RRF 融合。

效果：KB 级生产对齐评测（n=80）Recall@10 达 0.975、Recall@3 达 0.900；390 问离线测试 Recall 由 0.347 提升到 0.400（+5.3pp）。

举 例用户问「2024 年 Q3 退款政策里手续费怎么算」。纯向量可能只召回语义相近的一段，漏掉精确写「手续费 2%」的那句；BM25 恰好能精确命中「手续费」这个关键词。两者 RRF 融合后，既保证语义相关、又不丢精确条款。
如果追问「RRF 权重怎么定？重排序用什么模型？」——标准 RRF 是等权（1/(k+rank)），自适应加权可按查询类型调向量 / BM25 占比，具体策略以你实现为准；重排序简历没写具体模型，诚实说「轻量 cross-encoder 或规则打分」，别编。

你可以这样回答

核心原则：财务 / 数字场景错一个数就是事故，不能信模型自查。模型会「顺着自己编的答案自洽」，你让它检查自己，它大概率说「没问题」。

所以我用纯规则校验：答案里出现的每个数字，都去检索原文里强制对账——对不上就拒答并附原文。校验层是规则实现（AST 白名单求值，禁用 eval），根本不调模型。实测 1269 条测试集，正确回答误拒 0 条，关键数字幻觉率降至 0。

举 例原文写「账户余额 8,520 元」，模型若答成「余额约 9,000 元」，规则层拿到「9,000」去原文对账，发现对不上 → 直接拒答并附原文「余额 8,520 元」，而不是把错的「9,000」吐给用户。这里模型有没有「自觉」完全不影响结果。
如果追问「误拒 0 会不会漏拒（把错的放过去）？」——诚实答：误拒和漏拒是两条独立指标，测试集主要聚焦误拒；漏拒靠规则覆盖度 + 抽样评测兜底，承认这是「持续补规则的活」，比装完美更可信。

你可以这样回答

因为召回高 ≠ 答得好。差距来自三处：① 检索到了，但生成阶段没用对（指令 / 拼接问题）；② 多模态或复杂意图路由或理解出错；③ 护栏主动拒答（2.8%）本就不算「可用」。

所以可用率 88.8% 是「检索 + 生成 + 护栏」的联合结果，比单看召回诚实得多。另 RAGAS faithfulness 0.914，说明生成内容对检索依据的忠实度是达标的。

⚠ 高频追问这题面试官极可能主动问。务必抢在前面讲清「召回和可用率不是一回事」，这体现你对评测的理解，而不是被问住才解释。这是个加分项。
举 例某问句相关资料其实召回到了（Recall 算命中），但生成时模型把两段不相关的上下文拼在一起答非所问，或护栏发现数字对不上主动拒答——这两种情况召回是满的，可用率却掉。所以我会分开盯这两个指标，而不是只看一个。

你可以这样回答

多模态：图片先转文本 / 用视觉模型提取信息，再进入同一套检索与问答链路；意图路由决定走文本分支还是多模态分支。

记忆：短期用会话滑动窗口（保近因、控成本）；长期用户画像按用户 ID 隔离存储，避免不同用户串号。390 问端到端可用率 88.8%，拒答率 2.8%（11/390）。

举 例用户 A 上传了一张发票图片问「这张多少钱」，和用文字问「上次的发票多少钱」——前者走图片提取，后者从历史画像里取；因为画像按用户隔离，A 的发票不会串到 B 的会话里。

项目深挖 · triagent

一句话定位：模拟真实就医流程的多 Agent 分诊系统，用「固定规则 + 多 Agent 协作」解决单一大模型在医疗场景逻辑混乱、不安全的问题。技术栈 Java · Spring Boot 3.2 · Spring AI 1.0.0 GA · DeepSeek · Supervisor · MySQL · Redis。地址 http://114.215.186.113/triagent/

你可以这样回答

单一大模型在复杂医疗流程里容易「一步错步步错」，而且你很难定位它哪步跑偏了。分工能隔离职责、每个角色可被独立评测，所以我拆成多个 Agent。

角色有：预诊 Agent（收症状）、挂号 Agent（推荐科室）、评判 Agent（校验 / 仲裁）；Supervisor 负责调度与汇总——它不是把对话完全交给模型自由发挥，而是按流程状态决定下一步交给谁。

举 例用户说「胸口闷」：Supervisor 先派预诊 Agent 收症状，再派评判 Agent 看是不是红旗，若是就短路急诊；否则派挂号 Agent 推荐科室。每一步由 Supervisor 显式编排，而不是模型自己想到哪算哪。

你可以这样回答

急症走的是状态机强制短路：识别到红旗症状（如胸痛、意识障碍），直接走急诊分支，根本不经过模型推理。因为纯规则匹配、无 LLM 调用，所以 0 次模型调用、6–24ms 返回。

安全上是双重校验：「固定规则 + LLM-as-Judge」——规则保底线（安全绝对不依赖模型），Judge 只做软性质量。实测 30 例 golden set 双轨评测，29 例分诊科室命中，安全性 29/29 全通过，判轻（危险方向）0 例。

举 例用户说「突然胸痛伴大汗」，规则命中「胸痛」红旗 → 立刻返回「请立即前往急诊 / 拨打 120」，不调用任何模型。哪怕此时模型因为某种原因不可用，这条安全链路也照样工作——这就是「安全不依赖模型」的含义。
如果追问「规则和 Judge 冲突听谁的？」——答规则优先（安全不可协商），Judge 只补充非安全维度的体验优化，绝不推翻安全结论。

你可以这样回答

多 Agent 最大的坑是「模型还记得不记得之前说过什么」。SessionFactStore 把每轮抽取出的结构化事实存成共享状态，后续 Agent 直接读这个状态，而不是靠模型回忆。

更重要的是冲突拦截：分诊一旦判定急症，结论进入共享状态；预约 Agent 在下单前读这个状态，命中急症就确定性拦截普通挂号。这就避免了「一边说你该去急诊、一边又给你挂普通号」的逻辑分裂。

举 例预诊 Agent 判定用户是心梗疑似（急症），这个事实写进 SessionFactStore。用户接着说「帮我挂个明天的号」，预约 Agent 下单前读状态发现是急症 → 直接拦下，提示先去急诊。没有任何一个 Agent 能绕过这条共享事实。

你可以这样回答

做了分级降级：Redis 抖动 → 本地内存兜短期；Redis 完全不可用 → 降级为无状态会话，核心问诊流程不依赖记忆也能跑。

为什么记忆丢了只告警不阻断？因为问诊是核心链路，记忆丢失影响体验但不致命；我用告警让运维感知到，而不是把用户挡在门外——可用性优先于完美记忆。

另外 SSE 下发事件流展示推理过程，增强用户对「它在认真分析」的信任。

举 例Redis 挂了，用户还能正常描述症状、拿到分诊建议（只是系统不记得他上一轮说过啥）；同时后台报警。如果是反过来——Redis 挂了就拒绝服务，那才是真事故。所以降级策略的核心是「核心链路永远不依赖非必要组件」。
如果追问「Spring AI 1.0 GA 和 LangChain4j 区别？」——答 Spring AI 更贴 Spring 生态、ChatClient/Advisor 抽象统一多模型；LangChain4j 更轻、Java 原生。CodeCanvas 用 LangChain4j、triagent 用 Spring AI，我两边都踩过，对比着选的。

技术栈追问（按 JD 维度）

这一节不背概念，背「你什么时候用过、为什么这么选」。下面每个点都给了可说的口径 + 实例。

  • ReAct / Plan-and-Execute / Supervisor 怎么选？ 单步工具调用 ReAct 够；长任务先规划再执行用 Plan-and-Execute；多角色协作用 Supervisor。CodeCanvas 用类 Plan-and-Execute 的状态机，triagent 用 Supervisor——都是按场景选的，不是跟风。
  • Tool Calling 和 Function Calling 区别？ 广义同义；Function Calling 是 OpenAI 早期叫法，MCP 把「工具」标准化成协议，Agent 能接任意兼容 MCP 的服务。Mira 就是按 MCP 对外输出。
  • Agent 怎么防止跑飞？ 状态机 / 工作流约束流转 + 工具白名单 + 沙箱隔离 + 确定性护栏兜底（三个项目分别对应这几点）。
  • Prompt 工程常用几招？ 角色 + 约束 + 少样本；结构化输出约束；把可变上下文外置（需求单）；错误反馈回灌重试。
实 例被问「为什么不用 ReAct 直接做 CodeCanvas」——答：长代码生成任务里 ReAct 自由文本容易跑偏且难回滚，我用显式状态机把「澄清/规划/生成/校验/修复」固化，出错只回修复阶段，这就是 Plan-and-Execute 思路。
  • 切片策略怎么定？ 按文档类型：技术文档按标题层级、问答按语义、表格按行；避免截断。Mira 用层级切片。
  • 向量 + BM25 为什么比单向量好？ 向量管语义、BM25 管精确关键词，互补；RRF 融合。
  • RRF / 重排序是什么？ RRF 按排名倒数融合多路结果；重排序用 cross-encoder 对候选精排，提升精度。
  • 长期记忆怎么隔离？ 按用户 ID 分区存储，会话级短期滑动窗口控成本。
  • 怎么评测 RAG？ 离线 Recall@K、端到端可用率、拒答率、RAGAS(faithfulness/answer_relevancy)；区分「检索好」和「答得好」（见 Mira Q3）。
实 例被问「RAG 效果怎么保证」——答：不只看召回。我用 Recall@10（0.975）盯检索，用端到端可用率（88.8%）和 RAGAS faithfulness（0.914）盯「答得好不好、忠不忠实」，三指标分开看。
  • Redis 防击穿 / 会话存储？ setIfAbsent 原子占锁防击穿；TTL 控生命周期；会话 / 事实存 Redis（triagent）。
  • MySQL 索引与事务优化？ 高频查询建联合索引、覆盖索引减少回表；事务粒度尽量小、避免长事务锁表。
  • SSE 和 WebSocket 区别？ SSE 单向服务端推、走 HTTP、自动重连，适合事件流（三项目都用）；双向交互才上 WebSocket。
  • nginx 路径前缀托管？ location 前缀反向代理 + 静态资源，多应用共用一个域名不同路径（/canvas/ /mira/ /triagent/）。
  • Docker 部署？ 镜像分层、多阶段构建减体积、systemd 管进程保活、nginx 前置。
实 例被问「三个项目为什么同一台服务器」——答：个人云主机，用 nginx 路径前缀（/canvas/、/mira/、/triagent/）反向代理三个应用，成本低、便于统一演示，systemd 保活。
  • Java 并发用过哪些？ 线程池、ConcurrentHashMap、原子类、CompletableFuture 编排异步；集合 / 并发 / 多线程是简历写明的基础。
  • Spring Boot 怎么独立交付？ 分层（controller/service/dao）、统一异常处理、配置外置、Actuator 健康检、打包 jar + systemd 保活。
  • Python 工程化？ FastAPI 异步接口、Pydantic 校验、pytest 做评测脚本（Mira 的 1269 条测试就是脚本跑的）。
实 例被问「怎么证明 Python 工程化能力」——答：Mira 的 1269 条护栏测试、390 问端到端测试都是用 pytest 脚本批量跑的，不是手工点的，这本身就是工程化习惯。

两处必准备口径（简历写到了，面试前必须能讲清）必看

⚠️ 这两项是简历「专业技能」里点名的开发模式，面试官极可能顺着挖。下面给可防御的标准说法，但具体实现细节请你对照自己代码确认——别照背一个你没真正跑过的版本。尤其重试次数和兜底策略，被追问第三层会露馅。

你可以这样回答

Advisor 是 LangChain4j 里围绕模型调用的拦截器链，类似 Servlet Filter / Spring Interceptor——在请求发出前、响应回来后插入逻辑，而且可以排序串联。

在 CodeCanvas 里我用它把横切逻辑从业务里摘出来，大致三条：① 上下文注入 Advisor——把固化后的需求单 + Token 预算拼进 system prompt；② 审计 / 日志 Advisor——记录每次请求的输入输出与耗时；③ 结构化输出 + 重试 Advisor——负责把模型输出解析成目标结构，失败按策略重试。

好处是链路可组合、可单独测试，业务代码只关心「调模型」，横切关注点全在链上。

实 例没有 Advisor 时，每个调用点都要手写「拼 prompt + 记日志 + 解析 + 重试」；有了 Advisor，这些变成可复用的拦截器。比如换 token 预算策略，只改注入 Advisor，不动业务。这就体现了「关注点分离」。
如果追问「Advisor 和直接包一层有什么区别？多个 Advisor 顺序怎么定？」——答：Advisor 统一了横切逻辑的接入点、可排序可复用、和 ChatClient 生命周期绑定；顺序按「注入 → 调用 → 解析 → 日志」的依赖关系排。
⚠ 以你代码为准上面是可防御口径。请打开 CodeCanvas 代码确认：你实际挂了哪几条 Advisor、各自做了什么。如果实际只用了一两条，就照实说，别把上面三条全认。

你可以这样回答

我用框架的结构化输出能力（LangChain4j 的 AiServices 返回 POJO，或 JSON Schema 约束），让模型按固定结构返回，而不是自由文本。这样下游才能稳定消费。

解析失败的处理是带重试 + 兜底：解析异常时，把「错误信息 + 原始输出」回灌进下一轮 prompt，让模型修正；最多重试 3 次。3 次仍失败，绝不把未解析内容透传给下游，而是走确定性兜底：返回安全默认 / 明确提示用户重试 / 降级到固定流程。

为什么重要：模型不是每次都吐合法 JSON，没有重试 + 兜底，下游直接崩。

实 例模型本该返回 {"file":"app.js","fix":"..."}，却吐了半句带 markdown 的代码块。第一次解析失败 → 我把「你返回的不是合法 JSON，请只返回 JSON」回灌重问；第二次还失败就再来一次；第三次仍失败 → 不把这段脏数据交给修复模块，而是提示「本次修复失败，请重试」或走人工兜底，保证系统不崩。
⚠ 重点核对你简历写的是「解析失败重试」，但没写具体几次和兜底。面试前务必打开代码确认：你实际重试几次？失败怎么处理？把上面「3 次 + 兜底」替换成你的真实实现，否则被追问第三层会露馅。这是你简历里风险最高的一处，务必本人确认。

行为面试（STAR：情境-任务-行动-结果）

行为题别只说「我学到了很多」。每题收尾都落到一个可验证的事实或数字，和项目经历互相印证。

你可以这样回答

方向：不是追热点。我做项目体感是——模型能力够了，缺的是把它做成稳定系统的工程能力，而这恰恰是我最想深耕的。

无实习：我用「三个已上线公网项目 + 开源仓库（有 star）+ 技术博客」替代一段观摩式实习。每个项目都有可验证的评测数字（比如 Mira 幻觉 0、triagent 危险误判 0），比「实习里打过下手」更有说服力。

实 例被问「没实习凭什么」——答：我的实习就是这三个项目。它们不是 demo，是公网可访问、有评测数据的系统；GitHub 仓库和线上 demo 现在就能打开给你看。我把「作品」当履历。

你可以这样回答

双非：不回避。坦诚学校平台有限，所以更靠自驱：独立做完并部署三个系统、啃下 Spring AI / LangChain4j 等框架、坚持写博客沉淀。

失败：准备一个真实例子，重点讲「怎么发现、怎么量化、怎么修、复盘出什么」。别编，编的经不起追问。

实 例（参考话术，请换成你真事）早期做长任务生成时，我把整段历史每轮都重发，第 8 轮直接 token 爆炸、成本失控。后来量化发现注入量随轮数线性涨，才设计了需求固化——把单轮压到 7k、综合成本降 75%。这就是我「成本意识」的来源，不是书上看的。

你可以这样回答

协作：学校项目多为独立开发，诚实说；同时强调「能独立交付」是中小团队看重的，我也愿意在 code review / 文档 / 对齐这些协作流程上补。

规划：1–2 年吃透 Agent 工程化落地（成本 / 质量 / 安全三角），3–5 年能独立负责一条 AI 产品线。

实 例被问「你都是单干，能协作吗」——答：我确实独立交付多，但正因为一个人扛全流程，我特别懂「上下游接口要稳定、文档要说清」——这正是协作的底层能力。进团队我会主动补 review 和文档习惯。

反问清单（问面试官，别只说「没啥问题」）

挑 2–3 个和岗位最相关的问。问「痛点」和「评测」最能体现工程思维。

你可以这样问

「团队现在 AI / Agent 落地到哪一步了？技术栈是自研还是接开源框架？目前最痛的是效果、成本、还是落地稳定性？」

为什么问这题直接暴露对方是不是真在做 Agent、痛点是不是和你擅长的能力（成本 / 质量 / 安全）对得上。对得上就趁势讲你三个项目刚好覆盖这三角。

你可以这样问

「对校招生前 6 个月的期待是什么？有没有导师带？」「模型成本 / 幻觉治理这块，是算法侧还是工程侧在扛？」

为什么问前者看成长路径和团队是否愿意培养人；后者看岗位偏算法还是偏工程——你偏工程落地，问这个能帮你判断岗位匹配度，也顺带展示你关心「成本 / 幻觉」这种工程真问题。

你可以这样问

「（偏落地）你们怎么评测 Agent / RAG 的线上效果？有没有离线评测集？」

为什么问这题几乎是你简历的镜像——你 Mira 里写了 Recall@10 / 可用率 / RAGAS。问这个既显专业，又自然把话题引向你最有料的部分，让面试官觉得「这人真做过评测」。
